
## Overview
When facing a slowdown with an unknown cause, don't investigate randomly — use a structured checklist. There are two complementary methods depending on what you're looking at: **USE** for hardware/system resources, and **RED** for your own services/APIs.

## Key Concepts
- **USE method**: A checklist for diagnosing hardware/infrastructure resources (CPU, memory, disk, network).
- **RED method**: A checklist for diagnosing your own services or APIs (traffic, errors, speed).
- **p50/p95/p99**: Percentile measurements of request duration — showing the "typical," "slower than 95% of requests," and "slower than 99% of requests" times, respectively. These reveal outliers that averages hide.

## How It Works

### USE Method — For Hardware/System Resources
For **each** resource (CPU, memory, disk, network), ask three questions:

| Question | Meaning | Example |
|---|---|---|
| **U**tilization | How busy is the resource? | "CPU is at 95%", "disk is at 80% busy" |
| **S**aturation | Is work piling up waiting for it? | A queue of tasks waiting for CPU to free up |
| **E**rrors | Is it actually failing? | Dropped network packets, failed disk reads |

**Process**: Go through CPU, memory, disk, and network one at a time, checking all three questions for each. Whichever resource shows a problem first — high utilization, a backed-up queue, or real errors — is your bottleneck.

### RED Method — For Your Own Services/APIs
Track these three metrics for a service you own:

| Metric | Meaning |
|---|---|
| **R**ate | Requests per second the service is handling |
| **E**rrors | Requests per second that are failing |
| **D**uration | How long requests take — measured via **distribution** (p50/p95/p99), not just the average |

> Averages hide slow outliers — always check the percentile distribution instead of relying on a single average number.

## Important Details: When to Use Which

| Situation | Method to Use |
|---|---|
| Watching your own app/service (traffic, errors, speed) | **RED** |
| Watching the underlying machine/infrastructure (server, database box, network) | **USE** |

## Examples
- **USE in action**: Database queries are slow → check disk utilization → disk is at 95% busy with a growing I/O queue → disk saturation is the bottleneck.
- **RED in action**: API response times feel sluggish → check p99 duration → p99 is 3 seconds while average is only 200ms → a subset of requests are hitting a slow path, hidden by the average.

## Advantages
- Prevents random, unfocused troubleshooting
- USE and RED together cover both the infrastructure layer and the application layer
- Percentile-based duration tracking (RED) surfaces real user pain that averages mask

## Disadvantages / Limitations
- Requires monitoring/observability tooling already in place to gather these metrics
- USE method requires checking multiple resources systematically — can be time-consuming without automation
- Neither method pinpoints the *exact* code-level cause — they narrow down *where* to look, not *why* at the code level

## Related Concepts
- APM (Application Performance Monitoring) tools
- Percentile-based performance metrics (p50/p95/p99)
- Queueing and saturation in distributed systems
- Bottleneck analysis

## Summary
Use **USE** (Utilization, Saturation, Errors) to diagnose hardware/infrastructure resources like CPU, memory, disk, and network. Use **RED** (Rate, Errors, Duration) to diagnose your own services and APIs, paying special attention to duration percentiles rather than averages. Rule of thumb: **your app → RED**, **the machine underneath → USE**.
