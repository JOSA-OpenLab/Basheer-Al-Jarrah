
## Core Idea
> Every rule exists to reduce the reader's **cognitive load** — technical
> docs must move an idea from writer's head to reader's head with zero
> friction, often while the reader is stressed, stuck, or under time pressure.

Google's Developer Documentation Style Guide is the de facto reference for
clear technical English.

## Why This Guide Exists
- Working memory is limited (related to Miller's "7±2" concept)
- Every ambiguous pronoun, extra clause, or unfamiliar structure eats into
  that limited memory, leaving less room for the actual technical content
- Goal: **sentence structure should be invisible** — reader only thinks
  about the content, never the grammar

## The Six High-Leverage Rules

### 1. Active Voice
- ✅ "The parser reads the file."
- ❌ "The file is read by the parser."
- **Why:** Active voice front-loads the *actor* — reader instantly knows
  which component is responsible for what (useful for debugging: "go check
  the parser")
- **Exception:** Passive is fine when the actor is irrelevant —
  e.g. "Errors are logged to `stderr`"

### 2. Present Tense
- ✅ "Returns a list."
- ❌ "Will return a list."
- **Why:** Documentation describes a **standing fact** (true every time),
  not a one-time future prediction
- **Analogy:** "Water boils at 100°C" (law/fact) vs. "It will rain
  tomorrow" (forecast) — docs should read like the former

### 3. Second Person ("you"), Not First Person ("we")
- ✅ "You can install with pip."
- ❌ "We install with pip."
- **Why:** "We" is ambiguous (who is "we"?) and falsely implies
  collaboration. The reader acts **alone** at their keyboard — "you"
  matches that reality and matches natural imperative/command phrasing

### 4. Short Sentences
- **Heuristic:** If a sentence has two "and"s or a "however," break it up
- **Why:** Each extra clause is another fact the reader must hold in
  working memory *simultaneously* before the sentence resolves
- "However" is especially costly — it forces the reader to mentally revise
  everything that came before it

**Example fix:**
- ❌ "The parser reads the file and validates the schema, however if the
  schema is invalid it throws an exception and logs the error."
- ✅ "The parser reads the file and validates the schema. If the schema is
  invalid, it throws an exception. The error is also logged."

### 5. Sentence-Case Headings
- ✅ "Configure the database"
- ❌ "Configure The Database"
- **Why:** Title Case signals formality/marketing (book titles, movie
  titles). Sentence case reads as a direct instruction — which is what a
  doc heading actually is
- **Bonus:** Title Case capitalization rules are inconsistent across
  style guides; sentence case has one simple rule → consistent across
  many authors at scale

### 6. Ban "Easy," "Simply," "Just"
- ❌ "Simply install the package and you're done."
- **Why:** If the reader is reading docs, they don't yet know how to do
  the thing.
  - If it *is* easy for them → the word was useless
  - If it's *not* easy for them → the word makes them feel stupid instead
    of correctly blaming unclear docs
- These words are "either lies or condescending" — always written from
  the *author's* perspective (who already understands), never the
  *reader's* (who is currently stuck)
- **Fix:** Just delete the word. "Run `pip install flask`" loses nothing.

## How the Six Rules Connect
| Rule | Protects |
|---|---|
| Active voice + present tense | Clarity of **facts** (unambiguous actor, standing truth) |
| Second person | **Direct actionability** for the one person who matters |
| Short sentences | **Working-memory limits** (info delivered in digestible units) |
| Sentence-case headings | **Visual/formatting noise** reduction |
| No easy/simply/just | Reader's **emotional state** — no compounding self-doubt |

> [!important] Unifying philosophy
> Strip away everything that isn't the direct, neutral, actionable fact
> the reader needs — whether that's ambiguous grammar, excess clauses,
> decorative capitalization, or condescension.

## Full Before/After Example

**Before (violates nearly every rule):**
> "Configuration Of The Database"
> "The database will be configured by you, and once this is done the
> connection is easily established by the driver, however you should just
> make sure the credentials are correct."

**After (follows the guide):**
> "## Configure the database"
> "You configure the database in this step. The driver establishes the
> connection using your credentials. Make sure the credentials are correct."

## Common Misconceptions
- ❌ "Active voice means never use passive voice" — passive is fine when
  the actor doesn't matter
- ❌ "Short sentences = dumbed-down content" — it's about chunking, not
  reducing information density
- ❌ "'Just' is a harmless filler word" — in docs specifically, it reads
  as judgment on the reader's competence
- ❌ "This is only Google's house style" — Microsoft's Writing Style Guide
  and the plain-language movement converge on nearly identical rules,
  suggesting this reflects how people actually process instructions best,
  not arbitrary corporate preference

## Plain-Language Summary
Every rule exists to remove friction between what the writer means and
what the reader understands: say who does what plainly (active voice),
describe standing facts as standing facts (present tense), talk to the
reader directly (second person), give one idea at a time (short
sentences), keep formatting quiet (sentence case), and never make the
reader feel dumb for not already knowing the thing they came to learn
(no easy/simply/just).
