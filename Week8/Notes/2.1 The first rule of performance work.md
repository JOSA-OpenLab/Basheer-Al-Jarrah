
## Overview
Most code doesn't affect your program's speed. Only a small fraction — the parts that run repeatedly (loops, per-request handlers, hot paths) — actually determine how fast the program feels. Optimization efforts should be guided by measurement, not intuition.

## Key Concepts

- **Premature optimization**: Optimizing code before knowing whether it actually matters for performance. Donald Knuth called this "the root of all evil" because it wastes effort on the 97% of code that doesn't affect speed, while distracting from the critical 3% that does.
- **The 97/3 rule**: Roughly 97% of code has negligible impact on overall performance. The remaining 3% — usually loops, hot paths, or frequently-called functions — is where speed actually comes from.
- **Total impact**: The real cost of a piece of code is `(how often it runs) × (how slow it is)`, not how slow or "impressive" it looks in isolation.

## How It Works

1. **Measure first**
   Run a profiler before touching any code. Human intuition about "what's probably slow" is frequently wrong — profiling replaces guesswork with data.

2. **Fix by total impact, not appearance**
   Compare cost by execution frequency × time per execution:
   - A slow function that runs once (e.g., at startup) barely matters, even if optimized 10x.
   - A function that runs on every request matters enormously — small savings there multiply across every user, every time.

3. **Re-measure after the fix**
   Don't assume a change worked. Some "fixes" make things worse elsewhere. Always verify with numbers, not assumptions.

## Important Details

> Optimize based on **profiler data**, never on gut feeling about which code "looks slow."

- Startup/init code (`load_config()`, `connect_to_database()`) runs once per process lifetime → optimizing it yields negligible real-world benefit.
- Per-request code (`fetch_user()`, `render()`) runs thousands of times → even a 5ms improvement compounds massively over time.

## Examples

```python
def start_server():
    load_config()
    connect_to_database()
    # runs ONCE - total cost is irrelevant

def handle_request(req):
    data = fetch_user(req)
    return render(data)
    # runs THOUSANDS of times per minute
    # This is probably in the 3%
```

> If `start_server()` wastes 200ms, nobody notices — it happens once.
> If `handle_request()` wastes 5ms, that cost repeats on **every single request, forever**. That's where real performance work should focus.

## Advantages of This Approach
- Prevents wasted effort on code that doesn't matter
- Focuses engineering time on changes with real, measurable impact
- Reduces risk of introducing bugs while "optimizing" irrelevant code
- Backed by data rather than assumptions

## Disadvantages / Limitations
- Requires setting up and learning profiling tools
- Can feel slower upfront (measure → fix → measure again) vs. just "guessing and fixing"
- Profiling adds overhead and complexity to the workflow, especially for small projects

## Related Concepts
- Big-O complexity analysis (theoretical cost vs. real-world cost)
- Amdahl's Law (overall speedup is limited by the fraction of code you actually optimize)
- Hot path / cold path distinction in systems design
- Load testing and benchmarking

## Summary
Don't optimize by instinct — most code (~97%) doesn't matter for speed. Profile first to find the real bottlenecks, prioritize fixes by total impact (frequency × cost), and always re-measure after changes to confirm they actually helped.
